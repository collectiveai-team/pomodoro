# Cross-platform short audio playback for the Pomodoro/break alarm

- Issue: [collectiveai-team/pomodoro#10](https://github.com/collectiveai-team/pomodoro/issues/10) — "Investigar reproducción de audio corto multiplataforma para la alarma"
- Scope: Linux + macOS desktop only (no Windows). Python 3.14, PySide6/Qt6 (see [ADR-0001](../adr/0001-pyside6-for-gui.md)).
- Goal: find the simplest, most reliable way to play a short, togglable alarm sound (a beep or short packaged clip) at the end of a Pomodoro/break.

## 1. `QSoundEffect` (`QtMultimedia`) — reliability and backend requirements

`QSoundEffect` is Qt's purpose-built class for exactly this use case. The official docs describe it as designed "for playing low-latency sound effects, such as beeps, clicks... suitable for playing... game sound effects" and it "makes low latency, and hence low disk and CPU usage" its priority — [Qt 6 `QSoundEffect` docs](https://doc.qt.io/qt-6/qsoundeffect.html).

**Backends.** Qt Multimedia in Qt6 is built on a pluggable backend architecture. Per the official [Qt Multimedia overview](https://doc.qt.io/qt-6/qtmultimedia-index.html):

> "The main media backend, built on FFmpeg, ensures seamless cross-platform functionality, and is the default on all platforms except WebAssembly and embedded Linux/Boot2Qt."

- **FFmpeg backend** — the default on desktop Linux, macOS, and Windows since **Qt 6.5** (it shipped as a technology preview in Qt 6.4). This is confirmed by the Qt 6.5/6.7/6.11 versions of the same overview page all stating FFmpeg is the default outside WebAssembly/embedded-Linux.
- **GStreamer backend** — Linux-only, and per the docs "only available on Linux, and is only recommended for embedded applications"; it is the *default* only on embedded Linux/Boot2Qt, not desktop Linux — [Qt Multimedia GStreamer backend](https://doc.qt.io/qt-6/qtmultimedia-gstreamer.html). The same page also documents a known PulseAudio v16 bug that "causes the GStreamer pipeline to hang" on several distro versions (Ubuntu 22.04–24.04, Debian 11–12, Fedora 39–40) — irrelevant to us as long as we stay on the default FFmpeg backend.
- **AVFoundation backend** — native macOS/iOS backend, present but not the default (FFmpeg is preferred there too).
- The backend can be forced with the `QT_MEDIA_BACKEND` environment variable (`ffmpeg`, `gstreamer`, `darwin`, `windows`) — same overview page.

**Does `pip install PySide6` give a working backend out of the box?** Yes, with caveats:

- PySide6 ships FFmpeg binaries *inside the wheel*. Qt's own docs on [FFmpeg stub libraries on Linux and Android](https://doc.qt.io/qt-6/qtmultimedia-ffmpeg-stubs.html) explain that Qt bundles FFmpeg but patches its optional OpenSSL/VAAPI dependencies with dummy "stub" libraries (`libQt6FFmpegStub-*`) that "dynamically attempt to resolve real symbols via `QLibrary::load`" and "provide dummy implementations that return safe fallback values or no-ops" when the real libraries aren't present — i.e. the bundled FFmpeg is designed to work standalone without requiring the host to have matching system FFmpeg/OpenSSL versions.
- This is corroborated by real-world reports: a Raspberry Pi OS (Debian Bookworm) user found their PySide6 6.7.1 wheel's `libffmpegmediaplugin.so` was compiled against `libavformat.so.58` while the system had a newer/incompatible version — the bundled plugin was the thing failing, not a missing system package ([Raspberry Pi Forums thread](https://forums.raspberrypi.com/viewtopic.php?t=388488)). That is an ARM/version-skew edge case, not something expected on mainstream x86_64/arm64 desktop Linux or macOS.
- A separate, more common failure mode reported on the Qt Forum is `"No QtMultimedia backends found"`, traced to missing/mismatched shared libraries (e.g. `libavformat.so.58`, `libwebp.so.6`) especially on **minimal/headless environments and non-standard distros**, diagnosable via `QT_DEBUG_PLUGINS=1` — [Qt Forum thread](https://forum.qt.io/topic/159610/no-qtmultimedia-backends-found-only-qmediadevices-qaudiodevice-qsoundeffect-qaudiosink-and-qaudiosource-are-available).
- Regardless of decode backend, actual audio *output* on Linux still goes through the system audio server. The GStreamer backend page states plainly: "Audio features requires PulseAudio" ([Qt Multimedia GStreamer backend](https://doc.qt.io/qt-6/qtmultimedia-gstreamer.html)). Any normal desktop Linux session (PulseAudio, or PipeWire's pulse-compat shim, both ubiquitous on current distros) satisfies this; a bare headless/container environment with no audio server will not play sound regardless of backend.

**PySide6 packaging split.** Since PySide6 6.3, the `pip install PySide6` package is a thin alias that pulls in two real wheels — [`PySide6-Essentials`](https://pypi.org/project/PySide6-Essentials/) and [`PySide6-Addons`](https://pypi.org/project/PySide6-Addons/) — "which contains a predefined list of Qt Modules" (per the PyPI page text, also documented at [Qt for Python package details](https://doc.qt.io/qtforpython-6/package_details.html)). `QtMultimedia`/`QtMultimediaWidgets` are listed under **`PySide6-Addons`**, not `PySide6-Essentials`. Practical implication: a plain `pip install PySide6` already gets you `QtMultimedia` (it depends on both sub-wheels), but if this project ever switches to installing `PySide6-Essentials` directly to slim the install, `QtMultimedia` would need `PySide6-Addons` added explicitly.

## 2. Alternatives considered and ruled out

- **`QSound`** — the old Qt class for playing short sounds. It was **removed** in Qt 6. The official [Qt Multimedia changes in Qt 6](https://doc.qt.io/qt-6/qtmultimedia-changes-qt6.html) page lists it under "Removed features" with the explicit note: *"QSound: Use QSoundEffect instead."* (Its Qt5 docs page also pointed at `QSoundEffect`/`QMediaPlayer` — [Qt 5.15 `QSound`](https://doc.qt.io/qt-5/qsound.html).) Not usable on Qt6/PySide6 at all — confirmed moot.
- **`QApplication.beep()`** — per the [Qt 6 `QApplication` docs](https://doc.qt.io/qt-6/qapplication.html#beep), it "Sounds the bell, using the default volume and sound," and is unavailable "in Qt for Embedded Linux" (not our target anyway). It plays the OS's generic system bell — not a chosen/custom sound, not adjustable volume from the app, and its audibility depends entirely on the desktop environment's bell configuration (many Linux desktops mute/disable the terminal-style bell by default; there is no dedicated "alarm" affordance). Unsuitable as the primary alarm signal; only useful as a last-resort fallback beep, and even then `QSoundEffect` gives more control for basically the same effort.
- **Third-party Python audio libraries** — checked whether any give a compelling reason to add a dependency beyond PySide6:
  - **`simpleaudio`** ([PyPI](https://pypi.org/project/simpleaudio/)) — WAV-only, cross-platform, but its last release was 1.0.4 on 2019-11-29. Community reports (Snyk advisor, PyPI forks named `simpleaudio-patched`/`simpleaudio-312compat`) confirm it has had no release supporting Python 3.12+ and the original maintainer has said the project is effectively abandoned/orphaned, needing unofficial patched forks even to build on modern CPython. Given this project targets **Python 3.14**, `simpleaudio` is a non-starter without depending on an unofficial fork.
  - **`playsound`** ([PyPI](https://pypi.org/project/playsound/)) — pure Python, no declared deps, but last released 1.3.0 on 2021-07-24; its own docs say it uses `AppKit.NSSound` on macOS and **GStreamer** on Linux (tested only against Ubuntu 14.04/ElementaryOS Loki in the docs) — i.e. on Linux it has the exact same GStreamer dependency concern we're trying to avoid, but through an unmaintained, non-Qt-integrated wrapper.
  - **`pygame.mixer`** — works fine as an audio player, but pulls in the entire SDL2-based `pygame` package (video, joystick, font subsystems, etc.) merely to play one short clip — clearly disproportionate given PySide6/Qt already ships a fit-for-purpose class.
  - **`sounddevice`** — a low-level PortAudio binding operating on raw NumPy arrays/PCM buffers; it would require decoding the WAV ourselves (e.g. via `wave`/`numpy`) and adds a NumPy + PortAudio dependency chain for no benefit over `QSoundEffect`.
  
  None of these clears the bar of "actually simpler or more reliable than what PySide6 already includes." `QSoundEffect` is sufficient; no additional dependency is justified.

## 3. Supported audio format & packaging

**Format.** The [Qt 6 `QSoundEffect` docs](https://doc.qt.io/qt-6/qsoundeffect.html) describe the class as intended for "uncompressed audio files (typically WAV files)" and expose `QSoundEffect::supportedMimeTypes()` to query what the current platform/backend actually supports at runtime — but the doc page itself does not commit to a fixed list, deferring to the runtime check. This is consistent with long-standing community experience (Qt Forum threads on `QSoundEffect` decoding errors) that MP3/Ogg/Opus are unreliable or unsupported across platforms/backends, while uncompressed PCM WAV is the one format that works everywhere. **Decision: ship the alarm as a short, uncompressed PCM WAV** (mono, 16-bit, 44.1 kHz or 48 kHz is plenty for a one-off beep/chime, and keeps the file tiny).

**Packaging.** Two options exist:

1. **Qt Resource System (`.qrc` + `rcc`)** — compiles assets into a binary blob (or Python module via `pyside6-rcc`) referenced with a `qrc:/` URL. Adds a build step (running `pyside6-rcc`) and an extra generated file to keep in sync.
2. **Plain file shipped as Python package data**, loaded by filesystem path at runtime (e.g. via `importlib.resources`) and turned into a `QUrl.fromLocalFile(...)` for `QSoundEffect.setSource()`.

For a single short asset, option 2 is simpler, requires no extra build tooling, and is easy to unit-test (just check the file exists / assert `QSoundEffect.status()`). **Recommendation: ship the `.wav` as ordinary package data** inside the `pomodoro` package (e.g. `pomodoro/assets/alarm.wav`), resolved at runtime with `importlib.resources.files("pomodoro.assets") / "alarm.wav"`. Note as a follow-up: this repo's wheel is built with `hatchling` and `[tool.hatch.build.targets.wheel] packages = ["pomodoro"]` (see `pyproject.toml`); confirm the packaged `.wav` actually lands in the built wheel (hatchling includes non-Python files under the package directory by default, but it's worth a `python -m build` + `unzip -l` sanity check once the asset is added, since this is not currently exercised by any packaged data file in the repo).

## 4. Known platform-specific issues

**macOS.**
- No official Qt documentation surfaces macOS-specific codesigning/sandboxing requirements for local `QSoundEffect` playback in a normal (non–App Store sandboxed) desktop app; nothing in the `QSoundEffect` or Qt Multimedia docs mentions entitlements for this case.
- A real, commonly hit gotcha (reported on the [Qt Forum](https://forum.qt.io/topic/126897/no-sound-with-qsound-or-qsoundeffect-without-using-qeventloop)): `QSoundEffect` **requires a running Qt event loop** to actually emit sound — calling `play()` without `QApplication::exec()` (or an active `QEventLoop`) running produces silence. This is not macOS-exclusive, but it's the issue people most often hit there when testing `QSoundEffect` outside a full running app (e.g. in a quick script or a unit test). Non-issue for the shipped app itself, since it always runs inside `QApplication.exec()`; worth remembering if we ever write an isolated test/script that calls `.play()` without the main loop running.

**Linux.**
- Needs a reachable system audio server (PulseAudio, or PipeWire's PulseAudio-compatibility layer) — ubiquitous on current desktop distros, but absent in bare/headless containers ([Qt Multimedia GStreamer backend](https://doc.qt.io/qt-6/qtmultimedia-gstreamer.html), "Audio features requires PulseAudio").
- `"No QtMultimedia backends found"` can occur on minimal/atypical Linux setups (missing/mismatched `libavformat`/`libwebp` versions, ARM builds), diagnosable via `QT_DEBUG_PLUGINS=1` — [Qt Forum thread](https://forum.qt.io/topic/159610/no-qtmultimedia-backends-found-only-qmediadevices-qaudiodevice-qsoundeffect-qaudiosink-and-qaudiosource-are-available). Expected to be a non-issue on standard x86_64/arm64 desktop Linux distros (Ubuntu/Fedora/Debian and derivatives), which is our actual target; flagged here only so it's recognized quickly if a dev/CI machine ever hits it.
- No system packages (GStreamer, PulseAudio dev headers, etc.) need to be separately `apt`/`dnf`-installed for the default FFmpeg backend — the FFmpeg binaries ship inside the PySide6 wheel itself (§1).

## Recommendation

**Use `QSoundEffect` from `PySide6.QtMultimedia`. No third-party audio dependency is needed.**

- **API**: `QSoundEffect` — set the source with `QUrl.fromLocalFile(path)`, call `.play()` to fire the alarm, `.setLoopCount(1)` (default) so it plays once. Implement the "togglable" requirement trivially: when the user has the alarm disabled, simply skip calling `.play()` (or set `.setVolume(0)` / mute) — no need for a different code path.
- **Format**: a short, uncompressed **PCM WAV** clip (mono, 16-bit, 44.1/48 kHz), a few hundred ms to ~2s long. Do not use MP3/OGG — not reliably supported by `QSoundEffect` across backends/platforms.
- **Packaging**: ship the `.wav` as plain package data under `pomodoro/assets/`, loaded via `importlib.resources` at runtime and passed to `QSoundEffect` as a local file `QUrl`. Skip the Qt Resource System (`.qrc`/`rcc`) — unnecessary build-step overhead for a single asset. Verify the asset is actually included in the built wheel once added (hatchling should include it automatically given the current `packages = ["pomodoro"]` config, but this hasn't been exercised yet in this repo).
- **Dependency footprint**: none beyond the already-ADR-approved PySide6 dependency (see [ADR-0001](../adr/0001-pyside6-for-gui.md), which already anticipated `QSoundEffect` for this exact purpose). `pip install PySide6` is sufficient — it transitively includes `PySide6-Addons` (which carries `QtMultimedia`) and bundles a working FFmpeg-based backend for both Linux and macOS with no separate system package installation required for our target (mainstream desktop Linux distros + macOS).
- **Ruled out**: `QSound` (removed in Qt6), `QApplication.beep()` (generic, non-custom system bell — unsuitable as the actual alarm, at best a fallback), and `simpleaudio`/`playsound`/`pygame.mixer`/`sounddevice` (unmaintained and/or Python-3.14-incompatible, and/or disproportionately heavy, and/or reintroducing the same Linux GStreamer dependency concern this research set out to avoid).
- **Watch-outs to remember during implementation**: make sure `.play()` is only ever invoked while the app's `QApplication` event loop is running (always true in the real app; relevant if writing a standalone smoke-test script); if a headless CI test ever needs to exercise this code path, expect it to need either a virtual/PulseAudio-less audio sink or to be skipped/mocked, since there's no audio server in typical headless CI containers.
